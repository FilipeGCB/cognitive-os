# Run a reversible pilot before committing to the platform migration

**Test before commitment.** The new platform is promising, but the evidence is not strong enough to justify a full migration. A bounded pilot preserves upside while making the most important unknowns observable.

## Why this path wins

A full migration creates high switching cost before reliability, operating burden and real-user adoption are known. Doing nothing avoids migration risk but leaves the current bottleneck untouched.

The pilot dominates because it is reversible and directly tests the uncertainties that could still reverse the recommendation.

## Alternatives

| Path | Main advantage | Main sacrifice |
|---|---|---|
| Full migration now | Fastest theoretical transformation | High blast radius before evidence |
| Keep current system | Lowest immediate disruption | Bottleneck and opportunity cost remain |
| Bounded pilot | Real evidence with limited downside | Some temporary duplication |

## What could still change the decision

The leading risks are operational instability, hidden integration effort and low user adoption. If the pilot shows any of these beyond the proposed acceptance threshold, the migration should stop rather than expand by inertia.

Because comparable migrations vary widely and no defensible reference-class dataset is available in this example, no numerical base rate is asserted.

## Next proof

Pilot one representative workflow for four weeks. Measure reliability, manual intervention, user completion and integration effort. Predefine the threshold that would justify expansion and the kill criterion that would end the migration path.

If the pilot passes, prepare the staged migration plan. If it fails, preserve the existing system and use the observed failure as the next design input.
