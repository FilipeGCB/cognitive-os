# Cognitive OS V1.5 — Final Closure Checklist

**Status:** final release closure; no new product scope  
**Date:** 2026-09-05  
**Branch:** `feat/cognitive-os-v1-5`

## Purpose

This document is the hard end line for Cognitive OS V1.5. The project owner expanded the final closure on 2026-09-05 only to close already-discussed product obligations: mandatory Find Skills/Find MCP discovery, deployed opt-in telemetry with an evidence-driven improvement queue, and real OpenAI/Claude distribution surfaces. Those items are now implementation work, not V1.6 ideas.

The approved closure design is [`docs/superpowers/specs/2026-09-05-v1.5-product-closure-distribution-design.md`](../superpowers/specs/2026-09-05-v1.5-product-closure-distribution-design.md).

From this point onward, do not add another feature, adapter, provider, dashboard, analytics product or methodology expansion. Only blocker fixes, evidence/contract corrections, host validation and stable-release metadata are allowed.

- Discovery never authorizes installation/execution of a discovered candidate.

The old release statement that no production collector exists is obsolete.

- Shared diagnostics remain `OFF` by default.
- Consent is explicit opt-in, never preselected, revocable and separate from installation consent.
- Declining diagnostics does not reduce Cognitive OS functionality.
- The deployed collector endpoint is `https://wsqumhrcdwgoskolziuy.supabase.co/functions/v1/cognitive-os-telemetry`.
- Application data is isolated under the private `cognitive_os` database schema with RLS/no direct public table writes.
- Real HTTP smoke proved: missing consent -> `403`; schema-valid opted-in events -> `202`.
- Repeated bounded failure signatures enter `cognitive_os.improvement_queue`; three distinct accepted matching events promote `observing -> candidate`.

## Remaining required work before stable `v1.5.0`

### 1. Freeze the final behavioral candidate

The implementation scope is closed. Subsequent commits may only fix a failed gate, correct release evidence/claims, perform host-validation wiring, or promote stable metadata.

### 2. Run fresh remote behavioral conformance

Historical behavioral evidence that used local models remains historical only. Stable promotion requires a fresh run using the current remote-only workflow:

- explicit remote SUT provider, base URL and model;
- explicit independent remote grader provider, base URL and model;
- candidate SHA bound into the evidence;
- no implicit local/Ollama fallback;
- critical-case accounting preserved;
- fail closed when provider/model identity is unavailable.

This remains a real release blocker.

### 3. Host validation without Hermes lock-in

Hermes is **not part of Cognitive OS** and is not a dependency users must install. It is one optional compatibility host.

The release must not make universal support claims based on one host. Current packaging evidence already covers Codex/Claude/Gemini installation surfaces and the OpenAI MCP protocol path.

- A Hermes live E2E may be recorded as additional host-compatibility evidence when the Hermes runtime is available.
- Hermes being unavailable does not block the core release unless the release notes explicitly promise a Hermes-verified claim.
- Any Hermes account-bound NotebookLM invocation still requires explicit run consent and truthful `NOT_CALLED/BLOCKED/UNAVAILABLE` states when not authorized.

### 4. Resolve ChatGPT host claim

Before claiming **ChatGPT-host verified** rather than merely **submission-ready**:

- connect the deployed production MCP endpoint in ChatGPT Developer Mode;
- exercise `find_mcp` and `telemetry_status` from the actual host;
- render and interact with the consent widget;
- prove that a declined consent sends nothing;
- prove one explicitly approved diagnostic send;
- record the actual host/version/surface evidence.

If this smoke cannot be executed before core release, publish the OpenAI package truthfully as `SUBMISSION_READY / HOST_SMOKE_PENDING` and do not claim ChatGPT-host verification. That narrower claim is allowed; a fabricated `PASS` is not.

### 5. External plugin-directory state

Repository readiness and public directory publication are different states.

- Claude/OpenAI public submission/review may be initiated only through the current platform workflow available to the maintainer.
- Public availability must be claimed only after the external platform reports approval/published state.
- Waiting for third-party review does not justify keeping the Cognitive OS core permanently in `1.5.0-dev` if all release gates and truthful distribution claims are otherwise satisfied.

### 6. Promote release metadata to stable `1.5.0`

Only after the final behavioral candidate and required release claims are fixed:

- synchronize `skills/cognitive-os/VERSION`, `.codex-plugin/plugin.json`, Claude marketplace metadata and all distribution manifests;
- update changelog/release notes;
- refresh machine-verifiable release evidence for the final candidate and allowed release-only commits;
- bind evidence/manifests to the final candidate SHA as required by the release contract;
- re-run secret/PII/privacy/distribution/reference validation.

### 7. Final release path

- final deterministic/package/privacy/CI run green;
- independent release-evidence/claims review;
- remove Draft status from PR #5 only after the remaining blockers are closed according to the truthful release claim;
- merge PR #5 to `main`;
- run post-merge validation;
- create `v1.5.0` only from the verified `main` SHA.

## Explicitly outside V1.5 after this closure

The following are not forgotten debt and must not reopen the V1.5 scope:

- new capability adapters/providers beyond those already committed;
- additional discovery registries beyond Find Skills + Official MCP Registry;
- richer telemetry dashboards/BI/analytics products;
- automatic code/spec mutation from telemetry without normal review/promotion;
- new methodology lenses/workflows unrelated to a release blocker;
- generalized hosted agent runtime/SaaS architecture;
- making Supabase part of the Cognitive OS reasoning core.

## Definition of done

V1.5 is complete when the fresh remote behavioral conformance passes, all release claims are narrowed to evidence actually observed, stable `1.5.0` metadata/evidence is synchronized, final CI is green, PR #5 is merged, and `v1.5.0` is published.

Hermes compatibility and public marketplace review are recorded independently from the core product unless the release explicitly promises those verified claims. After `v1.5.0`, any new improvement is V1.6+ unless it is a security/correctness hotfix.
