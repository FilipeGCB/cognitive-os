# Cognitive OS V1.5 — Final Closure Checklist

**Status:** scope freeze for stable V1.5 closure  
**Date:** 2026-09-05  
**Branch:** `feat/cognitive-os-v1-5`

## Purpose

This document defines the narrow closure boundary for Cognitive OS V1.5. Its purpose is to prevent further scope creep. After this freeze, new features, new adapters, broader telemetry operations, and new discovery integrations belong to a later version unless they are strictly required to fix a release blocker.

## Already complete

- V1.4 remains the stable public baseline on `main`.
- V1.5 core implementation is present on the candidate branch.
- Deterministic suite is green (`157/157` in the recorded candidate evidence).
- V1.4 regression coverage is green.
- Historical V1.5 behavioral evidence exists, but it used local models and is retained as historical evidence only after the remote-only gate change.
- Distribution projection/smoke, schemas, privacy/PII controls, and public telemetry Gate T are recorded as passing.
- Telemetry defaults to `OFF` and shared telemetry remains fail-closed when no approved sender/endpoint exists.
- Standard branch CI is green on the scope-freeze commit.

## Required before stable V1.5

### 1. Freeze the behavioral candidate

No new feature work. Only blocker fixes, release-evidence corrections, and stable-promotion metadata changes are allowed.

### 2. Run fresh remote behavioral conformance

The V1.5 conformance workflow was changed to remove local-LLM gates. Stable promotion therefore requires fresh evidence using the current remote-only contract, not the older local-model result.

The final conformance run must:

- use an explicit remote SUT provider, endpoint and model;
- use an explicit independent remote grader provider, endpoint and model;
- bind the report to the final behavioral candidate SHA;
- preserve critical-case accounting and fail closed on unavailable provider/model identity;
- avoid any implicit fallback to Ollama or another local model;
- record the machine-verifiable report as release evidence.

Historical local-model conformance may remain in the repository for traceability, but it is not the final V1.5 promotion proof.

### 3. Close Hermes live E2E (Gate 9)

Produce fresh runtime evidence against the final behavioral candidate with:

- real Hermes runtime identity;
- explicit remote provider/model/endpoint identity;
- real tool invocation where the case requires it;
- explicit run consent before any account-bound capability such as NotebookLM is used;
- no false capability-execution claims;
- evidence bound to the actual run/session and candidate.

A blocked or unavailable capability must remain honestly `BLOCKED`/`UNAVAILABLE`/`NOT_CALLED`; it must not be converted to `PASS` by documentation alone.

### 4. Resolve ChatGPT Work verification (Gate 10)

The current V1.5 contract treats Work smoke as a release gate. Before stable promotion, choose one of two explicit outcomes:

- **Verified Work claim:** execute the documented smoke against the installed V1.5 artifact and record evidence; or
- **Narrower release claim:** formally change the spec/release contract so Work runtime verification is host-specific and non-blocking, while clearly publishing Work as `UNVERIFIED`/`UNAVAILABLE` rather than claiming support evidence that was not observed.

Do not silently reinterpret an `UNAVAILABLE` gate as `PASS`.

### 5. Promote release metadata to stable `1.5.0`

After the final behavioral candidate is fixed and the required runtime evidence is complete:

- synchronize `VERSION` and all distribution manifests;
- update changelog/release notes;
- regenerate or refresh machine-verifiable release evidence for the final candidate and allowed post-candidate release-only commits;
- validate source-tree/manifests/evidence binding;
- confirm no private markers, secrets, credentials, PII, or prohibited telemetry content are present.

### 6. Final release path

- run final deterministic/packaging/privacy/CI gates;
- perform final independent review of release evidence and claims;
- resolve Draft status only after blockers above are closed according to the chosen release contract;
- merge PR #5 to `main`;
- run post-merge CI/release gate;
- create stable `v1.5.0` tag/release only from the verified `main` SHA.

## Explicit non-blockers for core V1.5

These items must not expand the closure scope unless the release claim explicitly promises them:

- production deployment/operations of the private telemetry collector;
- enabling shared telemetry without an approved endpoint and host consent/sender capability;
- proving the exact identity of optional external Find Skills / Find MCP discovery assets; unknown identities remain blocked and no substitute is invented;
- new adapters, providers, discovery registries, dashboards, analytics surfaces, or telemetry products;
- README/launch polish outside the release-critical path, including the separate documentation PR #6.

## Definition of done

V1.5 is finished when the release boundary is explicit, fresh remote conformance satisfies the current gate contract, all host gates required by the chosen release claim are genuinely satisfied, stable metadata/evidence is bound to the final candidate, CI is green, PR #5 is merged, and `v1.5.0` is released.

After that point, any improvement request is V1.6+ unless it is a security or correctness hotfix.
