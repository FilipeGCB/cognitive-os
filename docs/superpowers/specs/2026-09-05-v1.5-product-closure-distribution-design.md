# Cognitive OS V1.5 Product Closure & Distribution Design

## Status

Approved for implementation by the project owner on 2026-09-05 as the final closure scope before stable `v1.5.0`.

## Goal

Close Cognitive OS V1.5 as a real distributable product: mandatory capability discovery on install, privacy-preserving telemetry with explicit consent and deployed collector, evidence-driven improvement queue, and packaging for ChatGPT/Codex and Claude-family hosts without weakening host neutrality or silently mutating user environments.

## Non-negotiable constraints

- No local LLM is used as a release/conformance gate.
- Find Skills and Find MCP discovery must exist after a successful Cognitive OS installation; they cannot remain abstract placeholders.
- Third-party candidate discovery never authorizes candidate installation or execution.
- Installation of Cognitive OS may install declared lightweight discovery dependencies only after the user accepts the installation terms for the bundle.
- Optional diagnostic sharing uses explicit opt-in. The telemetry checkbox/default is **OFF / unchecked** because consent must be affirmative, freely given, informed and revocable.
- Refusing telemetry must not reduce Cognitive OS functionality.
- Telemetry must never include prompts, responses, documents, file contents, private paths/URLs, cookies, tokens, credentials, free text, client/project names, PII or chain-of-thought.
- Self-improvement is evidence-driven but never silently self-modifies the active methodology. It may create a bounded improvement candidate/queue item; code/spec changes still require normal review and promotion gates.
- Public plugin publication is only claimed after the external platform accepts/publishes the submission. Preparation and deployed app endpoints are not equivalent to directory approval.

## Architecture

### 1. Mandatory discovery bootstrap

Two concrete discovery assets become canonical:

1. **Find Skills**
   - source: `https://github.com/vercel-labs/skills`
   - package/CLI: `skills`
   - pinned CLI version for V1.5: `1.5.23`
   - installed skill: `find-skills`
   - license: MIT
   - role: search/discover skills from the open Agent Skills ecosystem.

2. **Find MCP**
   - authoritative source: `https://github.com/modelcontextprotocol/registry`
   - production API: `https://registry.modelcontextprotocol.io/v0.1/servers`
   - pinned registry contract/release reference for V1.5: `v1.7.9`
   - role: search MCP servers by name using the official registry API.
   - implementation: a small Cognitive OS bundled read-only discovery client; the entire registry backend is **not** cloned or run locally.

This distinction matters: the user receives both discovery capabilities after installation, but we do not install an unnecessary copy of the official registry service.

### 2. Installer boundary

`bootstrap/cognitive_os_install.py` is the side-effectful installer boundary. Existing `cognitive_os_bootstrap.py` remains deterministic and side-effect-free.

The installer flow is:

1. show bundle terms and third-party dependency provenance;
2. require acceptance of installation terms;
3. install/copy Cognitive OS host package;
4. install `find-skills` with the pinned `skills@1.5.23` CLI where the host supports local Agent Skills;
5. verify `find-skills` visibility;
6. verify the bundled Find MCP client can reach/parse the official registry when network access exists;
7. present optional anonymous diagnostic sharing consent, default OFF;
8. store only the consent state/policy version locally;
9. produce an installation receipt with dependency states and no secrets.

Hosts that cannot modify a local machine (ChatGPT plugin/app and similar sandboxed hosts) package the same discovery behavior inside the plugin/app service instead of pretending to perform a local install.

### 3. Find MCP client

`bootstrap/cognitive_os_discovery.py` provides a pure/read-only client that:

- URL-encodes `search`;
- calls only the official `GET /v0.1/servers` endpoint;
- caps result count;
- validates the response shape before exposing candidates;
- returns provenance and raw server metadata required for the downstream Gauntlet;
- never installs/connects/calls the discovered MCP server.

### 4. Telemetry consent UX

Telemetry has three states:

- `OFF` — default, no local or remote diagnostics;
- `LOCAL_DIAGNOSTICS` — local sanitized trace only;
- `SHARE_PRIVACY_PRESERVING_DIAGNOSTICS` — sanitized trace may be sent after explicit opt-in.

The consent surface must display:

- purpose: improve Cognitive OS reliability and identify recurring failures;
- exact data categories sent;
- exact categories never sent;
- retention: sanitized detailed events 30 days, aggregates 12 months;
- collector destination/domain;
- how to revoke consent;
- privacy notice link;
- no feature penalty for refusal.

The share option is never preselected.

### 5. Deployed telemetry collector

A private collector is deployed as a Supabase Edge Function with a dedicated `cognitive_os` database schema.

Tables:

- `cognitive_os.telemetry_events`
  - sanitized structured events only;
  - unique `event_id` for idempotency;
  - bounded enums/text lengths;
  - 30-day retention target.

- `cognitive_os.improvement_queue`
  - aggregate issue signature only;
  - `component`, `failure_class`, `result`, `capability` and occurrence counters;
  - no free text/user content;
  - status lifecycle: `observing`, `candidate`, `accepted`, `rejected`, `resolved`;
  - repeated evidence promotes an item from `observing` to `candidate` at a deterministic threshold.

The Edge Function:

- accepts only POST JSON;
- enforces payload size;
- rejects unknown fields;
- performs a second allowlist validation;
- stores no application-level IP/User-Agent/fingerprint;
- deduplicates by event ID;
- upserts the improvement queue by a server-derived signature;
- returns a non-identifying receipt.

### 6. Evidence-driven self-improvement

Self-improvement is a controlled loop:

`sanitized event -> aggregate signature -> improvement_queue -> threshold -> candidate -> future spec/PR -> tests -> review -> promotion`

It does **not** mean:

`runtime failure -> silently edit SKILL.md -> deploy`.

This preserves the existing self-improvement governance and prevents telemetry noise from changing methodology automatically.

### 7. Distribution surfaces

#### Agent Skills / local hosts

- canonical `skills/cognitive-os/SKILL.md` remains the portable core;
- host distribution manifests include mandatory discovery bootstrap requirements;
- installer/README documents one supported install command per host family where feasible.

#### Claude plugin

The existing `.claude-plugin` package becomes the Claude distribution surface and must reference the Cognitive OS skill plus mandatory discovery bootstrap/packaged discovery behavior appropriate to Claude Code.

#### ChatGPT/Codex plugin

The target is a **submission-ready plugin** containing the Cognitive OS skill and, where external execution is required, an MCP app service. Current OpenAI product behavior allows plugins to contain skills, apps and app templates. The app endpoint is deployed and tested first; public directory availability remains externally review-gated.

A minimal MCP app should expose only product-supporting operations that need server execution, such as:

- `find_mcp` — read-only Official MCP Registry discovery;
- `telemetry_status` — read-only diagnostics configuration/status;
- `submit_diagnostic` — opt-in write to the Cognitive OS collector, with explicit tool annotations and no raw user content.

The Cognitive OS reasoning workflow itself stays in the skill, not in a remote black-box agent runtime.

## Validation

Required before stable release:

1. deterministic tests for canonical discovery asset identity;
2. failing-then-passing tests for installer plan and consent defaults;
3. failing-then-passing tests for Find MCP query/response validation;
4. telemetry schema/client tests proving OFF by default and explicit opt-in;
5. collector database/security checks and Edge Function smoke test;
6. improvement queue aggregation test;
7. `tools/validate_skill_references.py` implemented and green;
8. README PR #6 content reconciled into V1.5 branch;
9. current branch CI green;
10. fresh remote behavioral conformance (remote SUT + independent remote grader; no local fallback);
11. Hermes Gate 9 fresh runtime evidence;
12. Work/ChatGPT host claim resolved by real smoke or narrower truthful claim;
13. stable `1.5.0` version/evidence sync;
14. PR out of Draft, merged, post-merge validation, tag/release `v1.5.0`.

## Definition of done

V1.5 is done only when all implementation items above are merged and all externally executable release gates are either passed with real evidence or explicitly marked with a narrower truthful release claim. Public ChatGPT Plugin Directory listing is a separate platform review outcome and is never falsely reported as complete before approval.
